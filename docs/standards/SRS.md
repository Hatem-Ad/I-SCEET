## 2. Introduction

### 2.1 Purpose

This Software Requirements Standards document (SRS) defines the rules, format, conventions, and quality criteria that all software requirements produced by the I-SCEET toolchain must satisfy. It governs the output of:

- M1 - which generates High Level Requirements (HLRs) stored in SRD
- M2 - which generates Low Level Requirements (LLRs) stored in SDDD

These rules shall be injected as constraints into the M1 and M2 AI module system prompts and shall be applied by the independent reviewer during verification of SRD and SDDD.

### 2.2 Scope

This document covers: requirement identification, structure, language rules, quality attributes, traceability rules, derived requirement handling, and forbidden patterns. It applies to all HLRs in SRD and all LLRs in SDDD regardless of the target project.

### 2.3 Referenced Documents

- RTCA DO-178C Section 5 - Software Requirements Process
- RTCA DO-178C Section 6 - Software Design Process
- PSAC - Plan for Software Aspects of Certification
- SDP - Software Development Plan
- SVP - Software Verification Plan
- SDS - Software Design Standards (governs the SDDD structure these LLRs are rendered into)

## 3. Requirement Identification Rules

### 3.1 Unique Identifier Format

Every requirement shall have a unique identifier following this mandatory format:

| Type | Format | Example | Scope |
|---|---|---|---|
| High Level Requirement | HLR-[SUBSYSTEM]-[NNN] | HLR-BOOT-001 | SRD - generated by M1 |
| Low Level Requirement | LLR-[SUBSYSTEM]-[NNN]-[XX] | LLR-CLK-002-01 | SDDD - generated by M2. [XX] is a 2-digit sub-requirement counter (zero-padded, starts at 01) for cases where one function needs more than one LLR |
| Derived HLR | HLR-[SUBSYSTEM]-[NNN]-[XX]-D | HLR-SYS-007-02-D | SRD - derived. NNN is the fixed requirement ID and never changes; XX increments each time this specific derived HLR is revised. |
| Derived LLR | LLR-[SUBSYSTEM]-[NNN]-[XX]-D | LLR-FLASH-004-01-D | SDDD - derived. Same rule: NNN fixed, XX increments each time this specific derived LLR is revised. Traceability field is still set to Derived in addition to the -D ID suffix. |

*Note: derived HLRs and LLRs both carry a '-D' suffix at the end of their ID, after the [XX] counter. NNN is the fixed requirement identity and never changes once assigned; [XX] increments each time that specific derived requirement is individually revised. The Traceability field (LLR) / Upwards Traceability field (HLR) still records the Derived status independently of the ID suffix.*

### 3.2 Subsystem Codes

The [SUBSYSTEM] field shall use the following standardized codes:

| Code | Subsystem |
|---|---|
| BOOT | Bootloader - main bootloader initialization and jump logic |
| FLASH | Flash Driver - internal flash read/write/erase operations |
| UART | UART Driver - serial communication peripheral driver |
| CLK | Clock / RCC - system clock initialization and configuration |
| GPIO | GPIO Driver - general purpose input/output peripheral driver |
| CRC | CRC Module - firmware integrity verification |
| TICK | System tick / timebase |
| WDG | Watchdog |
| APP | Application-level logic |
| SYS | System / cross-cutting - error handling, system-level behavior |

For future projects, new subsystem codes shall be defined in the PDS before M1 is run.

### 3.3 Numbering Rules

- Numbers start at 001 and increment by 1 sequentially within each subsystem
- For LLRs, the [XX] sub-counter starts at 01 for the first LLR under a given [NNN]; a new [NNN] is used for each distinct requirement, not a new [XX] under an unrelated one
- Numbers shall never be reused, even if a requirement is deleted
- Deleted requirements shall be marked [DELETED] and retained for traceability
- Gaps in numbering are allowed and shall not be corrected by renumbering

## 4. Requirement Structure

### 4.1 Mandatory Fields - HLR (M1 output, SRD)

| Field | Mandatory | Description |
|---|---|---|
| ID | Yes | Unique identifier per Sec.3.1 |
| [COV.PDS-NNN] | Yes | Upward coverage tag to the parent PDS item |
| Capability title | Yes | Short descriptive title |
| Activation Period | If applicable | When this capability is active |
| Input Data / Output Data / Local Data | Yes | Data consumed/produced/local to this HLR |
| Requirement statement | Yes | The requirement text - 'The software shall...' |
| Upwards Traceability | Yes | Link to PDS item |
| Category | Yes | Functional / Performance / Interface / Safety / Resource |
| Context | Yes | Operating context this HLR applies in |
| Verification Method | Yes | Review / Analysis / Test / Demonstration |
| Security Assurance Level | If applicable | Per project security requirements |
| Safety Effect | Yes | Consequence if this HLR is violated |
| Rationale | Yes | Why this requirement exists |

### 4.2 Mandatory Fields - LLR (M2 output, SDDD)

An LLR is not a standalone shall-statement - it is a structured block covering both the enclosing function's interface and one or more requirement entries within it. Two field groups apply:

**Function-level fields (once per function):**

| Field | Mandatory | Description |
|---|---|---|
| Prototype | Yes | Exact C prototype |
| Parameters | Yes | Table: Data Name \| Access(R/W/R-W) \| Type \| Range \| Description |
| Pre-conditions | Yes | List, or None |
| Called Functions | Yes | List, or None - must stay consistent with the SDDD Architecture section and feeds ct_builder.py |
| Input Data / Output Data | Yes | IN: / OUT: / INOUT: bullets, one per {variable} |

**Requirement-level fields (one or more LLRs per function):**

| Field | Mandatory | Description |
|---|---|---|
| ID | Yes | LLR-[SUBSYSTEM]-[NNN]-[XX] per Sec.3.1 |
| [COV.HLR-xxx] | Required if Refined/Extended | Upward coverage tag |
| [JUS.[Rxx] section] | Required if Extended/Derived | Justification reference (optional for Refined only if a HW-specific detail is described) |
| Capability title | Yes | Short descriptive title |
| Causes / Effects | Yes | 2-column pipe table (Causes \| Effects); blank Cause = unconditional; rendered as a professional matrix by sddd_builder.py |
| Implementation | Yes | One bracketed line per distinct Cause/Effect label, exact bracket text must match the table |
| Traceability | Yes | Refined / Extended / Derived - must agree with the ID suffix (-[XX]-D present only when Traceability=Derived) |
| Mean-of-Verification | Yes | Precise enough for independent test generation; must not presuppose the implementation |
| Rationale | Required if Extended/Derived | '-' if Refined |
| [END_REQ] | Yes | Generic closing marker, no ID attached |

Data Dictionary tags ([VAR] / [CONST] / [TYPE]) are declared once per first use, immediately after Output Data and before the first LLR of that function - see SDS for the exact tag syntax; they feed dd_builder.py and are not rendered inside the LLR block itself.

### 4.3 Requirement Block Format - Real Examples

**HLR example (SRD):**

HLR-BOOT-001 / [COV.PDS-003] / capability title "Bootloader Startup Initialization" / Requirement: "The software shall initialize all required hardware peripherals within 100ms of power-on reset." / Upwards Traceability: PDS-003 / Category: Performance / Verification Method: Test / Safety Effect: Delayed boot could miss a safety deadline / Rationale: PDS-003 requires system ready within 500ms.

**LLR example (SDDD) - condensed from a real validated M2 output:**

Function configure_clock_source(): Prototype 'void configure_clock_source(TE_BOOT_CLK_freq source)'; Parameters table with source/R/TE_BOOT_CLK_freq/[enum values]/description; Called Functions: None; Output Data - OUT: {clock.fres_config.HSI}, OUT: {clock.fres_config.HSE}.

LLR-CLK-002-01 / [COV.HLR-CLK-002] / [JUS.[R01] 6.3.1] / "Configure Clock Source" / Causes-Effects table (HSI -> configure internal clock, HSE -> configure external clock) / Implementation: bracketed lines matching each cause/effect / Traceability: Refined / Mean-of-Verification: 'Verify the clock source is configured correctly.' / Rationale: - / [END_REQ]

## 5. Requirement Language Rules

This section applies to HLR statements and to LLR titles / Implementation lines. It does NOT apply to Causes/Effects table cells, which are technical conditions, not shall-statements.

### 5.1 Mandatory Language Pattern

Every HLR requirement statement shall follow this exact pattern:

| Pattern | Example |
|---|---|
| The software shall [action] [object] [condition/constraint] | The software shall initialize the UART peripheral at 115200 baud before accepting any input. |
| The software shall [action] [object] within [time constraint] | The software shall complete CRC verification within 50ms of firmware load. |
| The software shall [action] [object] when [trigger condition] | The software shall jump to the application vector when CRC verification succeeds. |
| The software shall [action] [object] if [error condition] | The software shall enter safe mode if the watchdog timer expires before initialization completes. |

### 5.2 Mandatory Keywords

| Keyword | Usage | Rule |
|---|---|---|
| shall | Mandatory requirement - DAL A | Use for all safety-critical requirements - ALWAYS lowercase |
| should | Recommended - non-mandatory | Allowed only for non-safety requirements - avoid for DAL A |
| may | Optional feature | Allowed only for optional behaviors - avoid for DAL A |
| will | Statement of fact / future | FORBIDDEN - use 'shall' instead |
| must | Informal obligation | FORBIDDEN - use 'shall' instead |
| can | Capability statement | FORBIDDEN - use 'shall' instead |

### 5.3 Forbidden Words and Patterns

| Forbidden Pattern | Reason | Correct Alternative |
|---|---|---|
| usually / generally / normally | Introduces ambiguity - not verifiable | State the exact condition explicitly |
| as much as possible | Not measurable - not verifiable | Provide a specific numeric limit |
| fast / quickly / soon | Relative terms - not measurable | Specify exact timing in ms or cycles |
| good / sufficient / adequate | Subjective - not verifiable | Define the quality metric explicitly |
| and/or | Ambiguous - two interpretations | Use separate requirements for each case |
| etc. / and so on | Incomplete - not verifiable | Enumerate all cases explicitly |
| user-friendly / intuitive | Subjective - irrelevant for embedded software | Remove or replace with measurable criteria |
| Passive voice without subject | Unclear who/what performs the action | Use 'The software shall...' explicitly |
| Multiple 'shall' in one statement | One requirement = one obligation | Split into separate requirements |
| TBD / TBC / TODO | Incomplete requirement - not certifiable | Complete before the document is baselined |

## 6. Requirement Quality Attributes

Every requirement in SRD and SDDD must satisfy ALL of the following quality attributes per DO-178C Sec.5.1:

| Attribute | Definition | Verification Method |
|---|---|---|
| Accurate | Correctly describes a real system need or behavior | Review against PDS / HLR parent |
| Consistent | No contradiction with any other requirement | Cross-reference review |
| Verifiable | Can be confirmed by Review, Analysis, Test, or Demonstration | Check verification method field is valid |
| Traceable | Links upward to a PDS item (HLR) or HLR (LLR) | Check COV/Traceability field is populated |
| Unambiguous | Only one interpretation possible | Independent engineer review |
| Complete | Contains all information needed for implementation and test | Review of all mandatory fields |
| Feasible | Can be implemented given hardware and timing constraints | Analysis against HW doc / architecture |

## 7. Traceability Rules

### 7.1 Upward Traceability (HLR -> PDS)

- Every HLR in SRD shall reference at least one PDS item via [COV.PDS-xxx]
- The PDS item ID shall exist in the provided PDS document - M1 shall not invent PDS IDs
- One PDS item may spawn multiple HLRs - this is normal and expected
- A PDS item with no corresponding HLR is a gap - M1 shall be re-run or the gap justified

### 7.2 Downward Traceability (HLR -> LLR)

- Every HLR in SRD shall be addressed by at least one LLR in SDDD via [COV.HLR-xxx]
- One HLR may be decomposed into multiple LLRs across one or more functions - this is the expected pattern
- A HLR with no corresponding LLR before M3 starts is a blocking defect

### 7.3 Derived Requirements

A derived requirement has no parent in the upstream document. It arises from design decisions or hardware constraints not captured in the PDS. Rules:

- Derived HLRs: convention unchanged from the previous baseline (-D suffix) - not re-verified against a fresh M1 audit this session
- Derived LLRs: carry the -[XX]-D ID suffix AND have Traceability = Derived (both must agree). [COV.HLR-xxx] is never used for a Derived LLR; [JUS.[Rxx] section] is mandatory instead
- All derived requirements shall be reviewed by the systems engineer before M2 (for derived HLRs) or M3 (for derived LLRs) is triggered
- All derived requirements shall be submitted to the safety assessment process per ARP4761

### 7.4 Traceability in the Traceability Matrix

M6 shall build the project's Traceability Matrix using the coverage tags of all requirements. The traceability chain is:

| Level | Links to | Stored in |
|---|---|---|
| PDS item | -> HLR-ID(s) | SRD, [COV.PDS-xxx] tag |
| HLR-ID | -> LLR-ID(s) | SDDD, [COV.HLR-xxx] tag |
| LLR-ID | -> /src file(s) | Source file header comment |
| LLR-ID | -> LLT case(s) | SUTC (Software Unit Test Case) |
| HLR-ID | -> HLT case(s) | SVTC (Software Verification Test Case) |

## 8. HLR-Specific Rules (M1 Output)

### 8.1 HLR Content Rules

- HLRs shall describe WHAT the software does - never HOW it does it
- HLRs shall be at the right abstraction level - no reference to specific registers, functions, or variables
- HLRs shall cover: functional behavior, performance constraints, interface requirements, and safety requirements
- HLRs shall not contain implementation details - these belong in LLRs

### 8.2 HLR Categories - All Must Be Covered

| Category | Description | STM32F303 Example |
|---|---|---|
| Functional | What the software must do | The software shall verify firmware CRC-32 before jumping to application |
| Performance | Timing, throughput, accuracy constraints | The software shall complete bootloader initialization within 100ms |
| Interface | Inputs, outputs, communication protocols | The software shall communicate via UART at 115200 baud, 8N1 |
| Safety | Failure modes, watchdog, error handling | The software shall trigger a system reset if watchdog expires during boot |
| Resource | Memory, stack, CPU usage limits | The software shall not use more than 4KB of RAM during bootloader execution |

### 8.3 System Architecture Section in SRD

- The architecture section shall be inserted verbatim - M1 shall not modify it
- HLRs shall be consistent with the provided architecture
- Any HLR that contradicts the provided architecture is a defect - M1 shall be re-run

## 9. LLR-Specific Rules (M2 Output)

### 9.1 LLR Content Rules

- LLRs shall describe HOW the software implements the HLR - specific enough for M3 to generate code directly from the Causes/Effects table and Implementation lines
- The Causes/Effects table is a structured representation of control flow, not decorative narrative - it must mirror the actual branching logic (if/else, loops) the function requires
- Every LLR shall be implementable within the single enclosing function
- LLRs shall not introduce functionality not traceable to an HLR - except for Traceability=Derived LLRs, which require [JUS.[Rxx]...] instead
- Every {variable} used in Input Data, Output Data, the Causes/Effects table, or the Implementation lines must have a matching [VAR] Data Dictionary declaration somewhere in the document

### 9.2 LLR Decomposition Rules

| Rule | Description | Example |
|---|---|---|
| One-to-many | One HLR may produce multiple LLRs across one or more functions | HLR-FLASH-001 -> LLR-FLASH-001-01 (erase), LLR-FLASH-002-01 (write), LLR-FLASH-003-01 (verify) |
| Multiple LLRs per function | A single function may need more than one LLR - use the [XX] suffix | configure_clock_source() -> LLR-CLK-002-01, LLR-CLK-002-02 if the causes genuinely split into independently-traceable requirements |
| No orphan LLR | Every LLR must carry [COV.HLR-xxx] or (if Derived) [JUS.[Rxx]...] | LLR-FLASH-004-01 must reference HLR-FLASH-001 or HLR-FLASH-002, or be marked Derived |
| No duplicate | Two LLRs shall not describe the same function behavior | If two LLRs both describe 'initialize UART', one must be deleted |
| Completeness | The union of all LLRs for a subsystem must fully implement every HLR in scope | If HLR-BOOT-001 requires 5 init steps, all 5 must appear across the subsystem's LLRs |

### 9.3 LLR Precision Requirements

- Timing values shall be specified in milliseconds (ms) or microseconds (us)
- Memory addresses shall be in hexadecimal (e.g., 0x08000000)
- Register and enum names shall match the target hardware reference manual exactly
- Function names in LLRs shall follow the naming convention defined in SCS
- Error codes shall be defined explicitly - no generic 'return error' statements
- Every distinct Cause and Effect label used in the table shall have exactly one matching bracketed line in Implementation, in the same order

## 11. Examples - STM32F303 Bootloader

### 11.1 Correct HLR Examples

| ID | Statement | Why it's correct |
|---|---|---|
| HLR-BOOT-001 | The software shall initialize all required hardware peripherals within 100ms of power-on reset. | Single 'shall', measurable (100ms), WHAT not HOW, verifiable by test |
| HLR-CRC-001 | The software shall verify the firmware image integrity using CRC-32 before executing any application code. | Clear trigger condition, specific algorithm, safety-relevant, testable |
| HLR-UART-001 | The software shall provide a UART communication interface operating at 115200 baud, 8 data bits, no parity, 1 stop bit. | All interface parameters specified, no ambiguity, fully verifiable |

### 11.2 Incorrect HLR Examples

| Bad Statement | Why it's wrong | Fix |
|---|---|---|
| The bootloader must start quickly. | 'must' forbidden; 'quickly' not measurable; no subject | The software shall complete bootloader startup within 50ms of power-on. |
| The software shall call HAL_Flash_Init() to initialize flash. | Describes HOW (function name) not WHAT | The software shall initialize the internal flash memory controller before any read or write operation. |
| The software shall handle errors and/or exceptions. | 'and/or' ambiguous; 'handle' vague; no specific condition | Split: one requirement for error detection, one for error recovery. |

### 11.3 Correct LLR Example (real, validated M2 output)

**Function: configure_clock_source()**

Prototype: void configure_clock_source(TE_BOOT_CLK_freq source)

Parameters: source | R | TE_BOOT_CLK_freq | [E_BOOT_CLK_HSI, E_BOOT_CLK_HSE, E_BOOT_CLK_PLL, E_BOOT_CLK_NB] | The clock source to configure

Output Data - OUT: {clock.fres_config.HSI}, OUT: {clock.fres_config.HSE}

**LLR-CLK-002-01**

[COV.HLR-CLK-002]

[JUS.[R01] 6.3.1]

Configure Clock Source

| Causes | Effects |
|---|---|
| The clock source is High-Speed Internal | Configure High-Speed Internal Clock |
| The clock source is High-Speed External | Configure High-Speed External Clock |

Implementation:

[The clock source is High-Speed Internal]: {source} is equal to E_BOOT_CLK_HSI

[Configure High-Speed Internal Clock]: Set {clock.fres_config.HSI} to TRUE

[The clock source is High-Speed External]: {source} is equal to E_BOOT_CLK_HSE

[Configure High-Speed External Clock]: Set {clock.fres_config.HSE} to TRUE

Traceability: Refined   |   Mean-of-Verification: Verify the clock source is configured correctly.   |   Rationale: -

[END_REQ]

*Why it's correct: table mirrors real control flow, every bracket has a matching Implementation line, Traceability/Mean-of-Verification/Rationale all populated, ID follows -NNN-XX format.*
