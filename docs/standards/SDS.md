## 2. Introduction

### 2.1 Purpose

This Software Design Standards document (SDS) defines the rules, constraints, and quality criteria that the software architecture and design produced by M2 must satisfy. It governs the structure of SDDD, covering Introduction, Architecture, Referenced Documents, Requirements (LLRs), and Summary.

These rules shall be injected as constraints into the M2 AI module prompt and shall be applied by the independent reviewer during verification of SDDD.

### 2.2 Scope

This document covers: SDDD structure, software architecture rules, module decomposition criteria, interface specification standards, data flow and control flow constraints, complexity limits, and coupling/cohesion rules. It applies to all architecture and design artifacts in SDDD regardless of the target project.

### 2.3 Referenced Documents

- RTCA DO-178C Section 6 - Software Design Process
- PSAC - Plan for Software Aspects of Certification
- SDP - Software Development Plan
- SVP - Software Verification Plan
- SRS - Software Requirements Standards (governs LLR writing rules)
- SCS - Software Code Standards (governs M3 output)

## 3. SDDD Document Structure

### 3.1 Mandatory Sections

SDDD generated by M2 shall contain exactly the following five Roman-numeral sections, mirroring the SRD structure:

| Section | Title | Content |
|---|---|---|
| I | Introduction | Purpose, scope (HLR range covered), DAL note, pointer to PSAC/SRD |
| II | Architecture | Static Architecture (functional decomposition, data coupling, control coupling, target constraints) and Dynamic Architecture (data/control flow narrative) |
| III | Referenced Documents | [Rxx] list - every reference used in a [JUS.[Rxx]...] tag in Section IV, and only those |
| IV | Requirements | One markdown sub-heading per function, containing Prototype / Parameters table / Pre-conditions / Called Functions / Input-Output Data (IN/OUT/INOUT) / Data Dictionary tags / one or more LLR blocks |
| V | Summary | LLR <-> HLR relationship table, one row per LLR emitted in Section IV |

### 3.2 Section II - Architecture Mandatory Content

| Sub-section | Content Required |
|---|---|
| Static Architecture - Functional Decomposition | List of all functions with a one-sentence role description each |
| Static Architecture - Data Coupling | Shared/global data used across more than one function, with producer(s)/consumer(s); must stay consistent with the [VAR] tags declared in Section IV |
| Static Architecture - Control Coupling | Cases where one function's behavior depends on control flags/state set by another function |
| Static Architecture - Target Constraints | STM32F303VCT6-specific constraints, only if relevant |
| Dynamic Architecture | Data flow / control flow narrative - which function calls which and what data moves between them; must stay consistent with each function's Called Functions field in Section IV |

### 3.3 Section IV - Requirements Mandatory Content (per function)

| Field | Content Required |
|---|---|
| Prototype | Exact C prototype |
| Parameters | Table: Data Name \| Access(R/W/R-W) \| Type \| Range \| Description |
| Pre-conditions | List, or None |
| Called Functions | List, or None |
| Input Data / Output Data | IN: / OUT: / INOUT: bullets, one per {variable} |
| Data Dictionary tags | [VAR]/[CONST]/[TYPE], declared once per first use, before the first LLR of the function |
| LLR block(s) | ID, [COV.HLR-xxx] and/or [JUS.[Rxx]...], title, Causes/Effects table, Implementation, Traceability, Mean-of-Verification, Rationale, [END_REQ] - see SRS for the full field-by-field specification |

The Causes/Effects table is a 2-column markdown pipe table (Causes | Effects), rendered by sddd_builder.py as a professional matrix (causes as column headers, effects as the data row beneath) - M2 does not need to produce the matrix layout itself, only the flat pipe table.

## 4. Module Decomposition Rules

### 4.1 Module Definition

A software module is the primary unit of decomposition in the I-SCEET architecture. Each module shall:

- Implement one or more related LLRs from a single subsystem (BOOT, FLASH, UART, CLK, GPIO, CRC, TICK, WDG, APP, SYS)
- Correspond to exactly one source file pair: [module_name].c and [module_name].h
- Have a single, clearly stated purpose expressible in one sentence
- Be independently compilable without modifying other modules

### 4.2 Module Naming Convention

| Level | Convention | Example |
|---|---|---|
| Module name | lowercase_snake_case | flash_driver, uart_driver, boot_manager |
| Source file | [module_name].c | flash_driver.c |
| Header file | [module_name].h | flash_driver.h |
| Init function | [module_name]_init() | flash_driver_init() |
| De-init function | [module_name]_deinit() | uart_driver_deinit() |
| Process function | [module_name]_process() | boot_manager_process() |
| Get function | [module_name]_get_[attribute]() | crc_module_get_result() |
| Set function | [module_name]_set_[attribute]() | uart_driver_set_baudrate() |

### 4.3 Module Decomposition Criteria

| Criterion | Rule |
|---|---|
| Single Responsibility | Each module implements requirements from exactly one subsystem code |
| High Cohesion | All functions in a module serve the same hardware peripheral or functional domain |
| Low Coupling | Modules communicate only through defined interfaces in their .h headers - no direct access to another module's internal variables |
| Complete Coverage | Every HLR in SRD shall be implemented by at least one module |
| Testability | Each module shall be independently testable with a module-level test harness (for M4 SUTC generation) |

### 4.4 Module Size Limits

*Sourcing note: DO-178C does not itself mandate specific numeric thresholds (function count, line count, etc.) - these limits are project-defined engineering practice, informed by DO-178C's general verifiability and structural-coverage objectives (Sec.6.3.4, Sec.9) rather than a literal citation. They were carried over unchanged from the previous edition of this document; if a precise DO-178C or MISRA-C citation is required for audit purposes, these values should be reviewed and sourced explicitly.*

| Metric | Limit |
|---|---|
| Maximum functions per module | <= 20 functions |
| Maximum source file size | <= 500 lines |
| Maximum header file size | <= 100 lines |
| Maximum module dependencies | <= 5 other modules |
| Minimum functions per module | >= 2 functions |

## 5. Interface Design Rules

### 5.1 Public Interface Rules

- All public functions shall be declared in the module header file
- All public data structures shall be defined in the header file
- No global variables shall be declared as public - use getter/setter functions
- All function parameters shall be explicitly typed - no void* without justification
- All functions returning error status shall use the project error code type (Sec.5.3)

### 5.2 Function Interface Standard

Every public function defined in SDDD and generated by M3 shall follow this interface pattern:

[ReturnType] [module_name]_[action]([ParamType] [param_name], ...);

Example (STM32F303 flash driver):

ISCEET_Status_t flash_driver_init(void);

ISCEET_Status_t flash_driver_erase_page(uint32_t page_address);

ISCEET_Status_t flash_driver_write(uint32_t address, const uint8_t* data, uint32_t length);

ISCEET_Status_t flash_driver_read(uint32_t address, uint8_t* buffer, uint32_t length);

### 5.3 Error Code Standard

All modules shall use the project-wide ISCEET_Status_t error code type (isceet_types.h): ISCEET_OK, ISCEET_ERROR, ISCEET_TIMEOUT, ISCEET_INVALID_PARAM, ISCEET_HW_FAULT, ISCEET_CRC_FAIL, ISCEET_FLASH_ERROR, ISCEET_BUSY.

### 5.4 Inter-Module Communication Rules

- Modules shall communicate only through function calls defined in public headers
- Shared data between modules shall use dedicated data structures - no raw global variables
- Callback functions shall be registered through explicit registration functions
- ISRs shall only set flags or write to ring buffers - no complex logic in ISRs

## 6. Complexity Limits

### 6.1 Cyclomatic Complexity

| Limit | Value | Action if Exceeded |
|---|---|---|
| Maximum CC per function (normal) | <= 10 | Refactor into smaller functions before M3 generates code |
| Maximum CC per function (safety-critical ISR) | <= 4 | ISRs must be minimal - raise PR if exceeded |
| Maximum CC per module (sum) | <= 50 | Module must be split into two or more modules |
| Target CC per function (ideal) | <= 5 | Preferred for DAL A - minimizes MC/DC test effort |

### 6.2 Nesting Depth Limits

| Context | Maximum Nesting Depth |
|---|---|
| General functions | <= 4 levels |
| ISR functions | <= 2 levels |
| Switch statements | <= 3 cases of nesting inside each case |

### 6.3 Function Length Limits

| Metric | Limit |
|---|---|
| Maximum lines per function (code only) | <= 60 lines (state machines may go to 100 with justification) |
| Maximum parameters per function | <= 6 (use a struct if more) |
| Maximum return points per function | <= 2 (prefer single exit; early return for error only) |
| Maximum local variables per function | <= 10 |

### 6.4 Architecture-Level Complexity

| Metric | Limit |
|---|---|
| Maximum number of software modules | <= 20 modules for the STM32F303 test project |
| Maximum call depth | <= 8 levels - must be analyzable statically (see the CT deliverable Activation Scenario) |
| Maximum number of interrupts | <= 8 active interrupt sources |
| Maximum interrupt nesting allowed | 0 - no nested interrupts for DAL A |
| Maximum shared resources between modules | <= 3 (protected by flags or mutexes) |

## 7. Data Design Rules

### 7.1 Data Type Rules

- All data types shall use fixed-width types from stdint.h: uint8_t, uint16_t, uint32_t, int8_t, int16_t, int32_t
- 'int', 'long', 'short' without width qualifier are FORBIDDEN
- 'float' and 'double' are FORBIDDEN unless explicitly justified and reviewed
- Boolean values shall use the project-defined boolean type or stdint uint8_t with defined TRUE/FALSE macros
- Pointer arithmetic is FORBIDDEN except in HAL and memory driver modules with explicit justification

### 7.2 Global Data Rules

- Global variables are FORBIDDEN except: ISR flag variables (volatile), one per interrupt source maximum
- Module state variables shall be static, not extern - not visible outside the module
- No dynamic memory allocation (malloc, calloc, free) is permitted anywhere in the design

### 7.3 Memory Map Rules

The software architecture in SDDD Section II (Static Architecture - Target Constraints) shall reproduce the authoritative memory map from PDS Sec.3.3 / ARCH Sec.8 exactly:

| Region | Address Range | Size | Content |
|---|---|---|---|
| Vector Table | 0x08000000 - 0x080001FF | 512 B | ARM Cortex-M4 interrupt vector table |
| Bootloader Code | 0x08000200 - 0x08007FF7 | ~31 KB | boot_manager + all drivers compiled |
| Firmware Metadata | 0x08007FF8 - 0x08007FFF | 8 B | App size (4B) + CRC-32 (4B) |
| Application Code | 0x08008000 - 0x0803FFFF | ~224 KB | Target application firmware image |
| RAM - Stack | 0x20000000 - 0x20001FFF | 8 KB | Bootloader stack - grows downward |
| RAM - Driver Buffers | 0x20002000 - 0x20003FFF | 8 KB | UART buffer, static module variables |
| RAM - Application | 0x20004000 - 0x20009FFF | 24 KB | Application stack + data |

## 8. Control Flow and Execution Model Rules

### 8.1 Execution Model

The STM32F303 bootloader shall use a bare-metal superloop execution model. Mandatory boot sequence (M2 must generate LLRs for each step):

- 1. Reset handler -> copy .data, zero .bss, call SystemInit()
- 2. CLK module -> configure HSE + PLL to 72MHz
- 3. GPIO module -> configure required pins
- 4. UART module -> initialize at 115200 baud for debug/update
- 5. FLASH module -> initialize flash controller
- 6. CRC module -> verify firmware CRC-32
- 7. BOOT module -> if CRC OK -> jump to application; if CRC FAIL -> enter update/error mode

### 8.2 Interrupt Architecture Rules

- ISR functions shall be defined only in the module responsible for the corresponding peripheral
- ISRs shall execute in less than 10us - documented as a design constraint in SDDD Section II
- ISRs shall only set a volatile flag or write to a ring buffer
- All ISR priority levels shall be defined in SDDD Section II (Dynamic Architecture) with justification
- No two ISRs shall share the same priority unless explicitly justified

### 8.3 Initialization Order

The initialization order of all modules shall be explicitly defined in SDDD Section II (Dynamic Architecture) and shall:

- Be consistent with hardware dependency order (clock before peripherals, peripherals before drivers)
- Assign a priority number to each module init function: lower number = earlier initialization
- Guarantee that no module's init function calls another module's non-init function

| A05 | Module dependencies are documented and no circular dependency exists |
| A06 | All public interfaces are defined in header files |

## 10. Examples - STM32F303 Bootloader

### 10.1 Correct Module Decomposition (SDDD Section II)

| Module Name | Source File | Purpose | Implements HLRs |
|---|---|---|---|
| boot_manager | boot_manager.c/.h | Main bootloader sequencing: init, verify, jump | HLR-BOOT-001, HLR-BOOT-002, HLR-BOOT-003 |
| clk_driver | clk_driver.c/.h | RCC configuration: HSE enable, PLL setup, AHB/APB prescalers | HLR-CLK-001 |
| flash_driver | flash_driver.c/.h | Internal flash: erase, write, read, verify operations | HLR-FLASH-001, HLR-FLASH-002 |
| uart_driver | uart_driver.c/.h | USART1 configuration, transmit/receive, interrupt handling | HLR-UART-001, HLR-UART-002 |
| crc_module | crc_module.c/.h | CRC-32 computation using STM32 hardware CRC unit | HLR-CRC-001 |

### 10.2 Correct LLR Example - Design Compliant (real, validated format)

**Function: configure_clock_source()**

Prototype: void configure_clock_source(TE_BOOT_CLK_freq source)

**Parameters:**

| Data Name | Access | Type | Range | Description |
|---|---|---|---|---|
| source | R | TE_BOOT_CLK_freq | [E_BOOT_CLK_HSI, E_BOOT_CLK_HSE, E_BOOT_CLK_PLL, E_BOOT_CLK_NB] | The clock source to configure |

**LLR-CLK-002-01**

[COV.HLR-CLK-002]

[JUS.[R01] 6.3.1]

Configure Clock Source

|  | Cause |  |
|---|---|---|
| Effect | The clock source is High-Speed Internal | The clock source is High-Speed External |
|  | Configure High-Speed Internal Clock | Configure High-Speed External Clock |

Implementation: [The clock source is High-Speed Internal]: {source} is equal to E_BOOT_CLK_HSI  |  [Configure High-Speed Internal Clock]: Set {clock.fres_config.HSI} to TRUE

Traceability: Refined   |   Mean-of-Verification: measure SYSCLK via MCO pin output and oscilloscope, expected 72MHz +/-1%   |   Rationale: -

[END_REQ]

*Why it's compliant: function decomposition matches Sec.II, register/clock names match the STM32F303 reference manual, Causes/Effects table mirrors real control flow, ID follows the LLR-[SUBSYSTEM]-[NNN]-[XX] format.*

### 10.3 Forbidden Design Patterns

| Pattern | Why Forbidden | Correct Alternative |
|---|---|---|
| extern uint32_t global_flash_address; | Global variable - visible across modules, untraceable writes | Use flash_driver_get_address() getter function |
| void* data parameter | Type-unsafe - hides actual type from reviewer | Use explicit typed parameter: uint8_t* data |
| malloc(sizeof(FlashBuffer_t)) | Dynamic allocation - heap fragmentation, non-deterministic | Declare static FlashBuffer_t buf; in module scope |
| while(!(FLASH->SR & FLASH_SR_BSY)) {} | Infinite busy-wait - no timeout protection | Add timeout counter; return ISCEET_TIMEOUT if exceeded |
| Nested ISR calls | Non-deterministic timing; stack overflow risk | Set flag in ISR; handle in main loop |
