## 2. Introduction

### 2.1 Purpose

This Software Code Standards document (SCS) defines the naming conventions, commenting rules, structural constraints, MISRA-C compliance requirements, and forbidden constructs that all source code generated by M3 must satisfy. It also defines the mandatory /src folder structure and file header format.

These rules shall be injected as constraints into the M3 AI module prompt and applied by the independent reviewer during code review of the /src folder.

### 2.2 Scope

This document applies to all C source files (.c) and header files (.h) generated by M3 in the /src folder, for the STM32F303 bootloader test project and all future I-SCEET target projects. Language standard: C99.

### 2.3 Referenced Documents

- RTCA DO-178C §7 — Software Coding Process
- MISRA-C:2012 — Guidelines for the Use of the C Language in Critical Systems
- PSAC001 — Plan for Software Aspects of Certification
- SDP001 — Software Development Plan
- SDS-001 — Software Design Standards (defines module structure M3 must follow)
- SRS-001 — Software Requirements Standards (LLR IDs referenced in file headers)

## 4. Naming Conventions

### 4.1 File Naming

| Item | Convention | Example |
|---|---|---|
| Source file | lowercase_snake_case.c | flash_driver.c |
| Header file | lowercase_snake_case.h | flash_driver.h |
| Module folder | lowercase_snake_case/ | flash_driver/ |
| Shared types file | isceet_types.h (fixed name) | isceet_types.h |

### 4.2 Function Naming

| Function Type | Convention | Example |
|---|---|---|
| Initialization | [module]_init(void) | flash_driver_init(void) |
| De-initialization | [module]_deinit(void) | uart_driver_deinit(void) |
| Main process | [module]_process(void) | boot_manager_process(void) |
| Getter | [module]_get_[attribute](void) | crc_module_get_result(void) |
| Setter | [module]_set_[attribute]([type] val) | uart_driver_set_baudrate(uint32_t baud) |
| Action | [module]_[verb]_[object]([params]) | flash_driver_erase_page(uint32_t addr) |
| ISR handler | [module]_IRQHandler(void) | uart_driver_IRQHandler(void) |
| Static internal | static [verb]_[object]([params]) | static compute_crc32(uint8_t* data) |

### 4.3 Variable Naming

| Variable Type | Convention | Example |
|---|---|---|
| Local variable | lowercase_snake_case | byte_count, flash_status |
| Static module variable | s_lowercase_snake_case | s_uart_initialized, s_crc_result |
| ISR flag (volatile) | g_[module]_[flag]_flag | g_uart_rx_ready_flag |
| Function parameter | lowercase_snake_case | page_address, data_length |
| Constant (macro) | UPPER_SNAKE_CASE | FLASH_PAGE_SIZE, MAX_RETRY_COUNT |
| Enum value | ISCEET_UPPER_SNAKE_CASE | ISCEET_OK, ISCEET_TIMEOUT |
| Typedef struct | PascalCase_t | FlashConfig_t, UartHandle_t |

### 4.4 Macro and Constant Naming

- All macros shall be UPPER_SNAKE_CASE with module prefix: FLASH_MAX_PAGES, UART_BUFFER_SIZE
- Boolean macros: ISCEET_TRUE (1u) and ISCEET_FALSE (0u) — never use bare 1 or 0 for boolean
- Magic numbers are FORBIDDEN — all numeric literals shall be named constants or macros
- Macro names shall clearly describe their value — no single-letter macros except loop counters

## 6. MISRA-C:2012 Compliance

### 6.1 Compliance Level

All source code generated by M3 shall comply with MISRA-C:2012 Mandatory and Required rules. Advisory rules shall be followed where practical. The compliance level per category is:

| MISRA-C Category | Rules | Compliance Level |
|---|---|---|
| Mandatory | ~10 rules | 100% — no deviation permitted under any circumstance |
| Required | ~100 rules | 100% — deviation requires formal documented justification |
| Advisory | ~50 rules | Best effort — documented when not followed |

### 6.2 Key MISRA-C Rules Applied

| Rule | Category | Description | Example Violation |
|---|---|---|---|
| Rule 1.1 | Required | All code shall conform to C99 | Using C11-only features like _Generic |
| Rule 2.1 | Required | A project shall not contain unreachable code | Code after return statement |
| Rule 2.2 | Required | There shall be no dead code | Unused variables or expressions |
| Rule 8.4 | Required | Functions shall be declared before use | Calling function without prototype |
| Rule 10.1 | Required | Operands shall not be of inappropriate essential type | Mixing signed and unsigned without cast |
| Rule 11.3 | Required | Shall not cast between pointer to object and integer type | (uint32_t)ptr arithmetic |
| Rule 12.1 | Advisory | Operator precedence — use parentheses | a + b << 2 without parentheses |
| Rule 14.4 | Required | Controlling expression of if/while/for shall be Boolean | if(x) where x is uint8_t |
| Rule 15.5 | Required | Function shall have single point of exit | Multiple return statements |
| Rule 17.3 | Mandatory | No function with variable number of arguments (no variadic) | Using printf() in production code |
| Rule 18.1 | Required | Pointer arithmetic within bounds only | ptr + n beyond array bounds |
| Rule 21.3 | Required | No use of malloc/calloc/free | Dynamic memory allocation |
| Rule 21.6 | Required | No use of standard I/O in production (stdio.h) | printf/scanf in embedded code |

### 6.3 Permitted Deviations

Deviations from Required MISRA-C rules are permitted only under the following conditions:

- A formal Deviation Record (DR-NNN) is created documenting: rule violated, location, justification, risk assessment
- The deviation is reviewed and approved by the independent reviewer and QA officer
- The deviation is referenced in the source code with a comment: /* MISRA-C:2012 Rule X.Y deviation — see DR-NNN */
- The deviation is listed in SVR-001 and STD

## 7. Forbidden Constructs

The following constructs are ABSOLUTELY FORBIDDEN in all M3-generated code — no deviation permitted:

| Construct | Reason | Alternative |
|---|---|---|
| goto | Unstructured control flow — untestable branches | Use structured loops and early return for errors |
| malloc / calloc / free | Non-deterministic timing; heap fragmentation | Use static allocation only |
| Recursion | Unbounded stack depth — stack overflow risk | Convert to iterative algorithm |
| printf / scanf (stdio.h) | Not suitable for embedded; large code footprint | Use UART driver functions directly |
| setjmp / longjmp | Bypasses normal control flow — untraceable | Use return codes and error propagation |
| Infinite loops without exit | Unverifiable termination — not MC/DC testable | Add timeout counter and exit condition |
| Variable Length Arrays (VLA) | Non-deterministic stack usage | Use fixed-size arrays with defined bounds |
| Multiple assignments in one line | a = b = c = 0 — ambiguous evaluation order | Use separate assignment statements |
| Implicit type conversion | Platform-dependent behavior | Use explicit casts with (type) |
| Bitfields | Implementation-defined bit ordering | Use bitmasks with uint8_t/uint16_t/uint32_t |
| Floating point (float/double) | Non-deterministic on Cortex-M without FPU config | Use fixed-point arithmetic (Q-format) |
| #undef | Redefining macros leads to ambiguity | Define macros once in header, never undef |
| Function-like macros with side effects | Evaluated multiple times — unpredictable | Use inline functions instead of macros |

## 8. Commenting Rules

### 8.1 Mandatory Comments

- Every .c and .h file shall have the mandatory file header (see §5)
- Every public function shall have the mandatory function header (see §5.3)
- Every #define constant shall have an inline comment explaining its value and units
- Every ISR function shall have a comment explaining the interrupt source and priority
- Every MISRA-C deviation shall have the deviation reference comment

### 8.2 Inline Comment Rules

- Inline comments shall use // style (C99 compliant)
- Block comments shall use /* */ style — never nested
- Comments shall explain WHY not WHAT — the code shows what, comments explain intent
- Commented-out code is FORBIDDEN — use version control (Git) instead
- TODO and FIXME comments are FORBIDDEN in baselined code

### 8.3 Comment Language

- All comments shall be written in English
- Technical abbreviations shall be defined on first use
- Register names shall match the STM32F303 Reference Manual (RM0316) exactly

### 8.4 Comment Examples

```
/* GOOD — explains WHY */
/* Delay 2ms after HSE enable to allow oscillator to stabilize (RM0316 §8.2.3) */
HAL_Delay(2U);
/* BAD — explains WHAT (obvious from code) */
/* Add 2 to counter */
counter += 2U;
/* GOOD — MISRA deviation reference */
/* MISRA-C:2012 Rule 11.3 deviation — see DR-001: HAL requires pointer cast */
reg_value = (uint32_t)(&FLASH->CR);  /* cppcheck-suppress misra-c2012-11.3 */
```

## 9. Code Structure Rules

### 9.1 Source File Structure

Every .c file generated by M3 shall follow this mandatory structure order:

```
/* 1. File header comment block */
/* 2. Includes — system headers first, then project headers */
#include <stdint.h>
#include <stdbool.h>
#include "stm32f3xx_hal.h"
#include "isceet_types.h"
#include "flash_driver.h"
/* 3. Private macros and constants */
#define FLASH_TIMEOUT_MS  (100U)
#define FLASH_KEY1        (0x45670123UL)
/* 4. Private type definitions */
typedef struct { uint32_t address; uint32_t size; } FlashRegion_t;
/* 5. Private (static) variable declarations */
static uint8_t s_flash_initialized = ISCEET_FALSE;
/* 6. Private function prototypes */
static ISCEET_Status_t wait_for_flash_ready(uint32_t timeout_ms);
/* 7. Public function definitions (with headers) */
ISCEET_Status_t flash_driver_init(void) { ... }
/* 8. Private function definitions */
static ISCEET_Status_t wait_for_flash_ready(uint32_t timeout_ms) { ... }
```

### 9.2 Include Guard Rule

Every .h file shall have an include guard using the following exact pattern:

```
#ifndef [MODULE_NAME]_H   /* e.g., FLASH_DRIVER_H */
#define [MODULE_NAME]_H
/* header content */
#endif /* [MODULE_NAME]_H */
```

### 9.3 Return Value Rules

- Every function that can fail shall return ISCEET_Status_t
- Void functions are permitted only for functions that cannot fail (e.g., pure register reads)
- Return values of all ISCEET_Status_t functions shall be checked by the caller
- Unchecked return values shall be cast to (void) with a justification comment

## 11. Code Examples — STM32F303 Bootloader

### 11.1 Correct Function Example

```
/**
 * @brief   Erase one flash page at the given address
 * @param   page_address  Start address of the page to erase (must be page-aligned)
 * @return  ISCEET_OK          if erase successful
 *          ISCEET_INVALID_PARAM if address not page-aligned
 *          ISCEET_TIMEOUT     if flash not ready within FLASH_TIMEOUT_MS
 *          ISCEET_HW_FAULT    if erase operation fails
 * @req     LLR-FLASH-002
 */
ISCEET_Status_t flash_driver_erase_page(uint32_t page_address)
{
    ISCEET_Status_t status;
    if ((page_address % FLASH_PAGE_SIZE) != 0U) {
        return ISCEET_INVALID_PARAM;
    }
    status = wait_for_flash_ready(FLASH_TIMEOUT_MS);
    if (status != ISCEET_OK) {
        return status;
    }
    /* Unlock flash, erase page, lock flash (RM0316 §4.3.3) */
    FLASH->KEYR = FLASH_KEY1;
    FLASH->KEYR = FLASH_KEY2;
    FLASH->AR   = page_address;
    FLASH->CR  |= FLASH_CR_PER | FLASH_CR_STRT;
    status = wait_for_flash_ready(FLASH_TIMEOUT_MS);
    FLASH->CR &= ~FLASH_CR_PER;
    FLASH->CR |= FLASH_CR_LOCK;
    return status;
}
```

### 11.2 Forbidden Code Examples

| Forbidden Code | Violation | Correct Version |
|---|---|---|
| uint8_t* buf = malloc(256); | Rule 21.3 — no dynamic allocation | static uint8_t buf[256U]; |
| printf("Init done\n"); | Rule 21.6 — no stdio in production | uart_driver_send_string("Init done\r\n"); |
| for(;;) { HAL_Delay(1); } | Infinite loop without exit condition | uint32_t t=0; while(t++ < TIMEOUT) { HAL_Delay(1U); } |
| if(flash_driver_init()); | Return value not checked | if(flash_driver_init() != ISCEET_OK) { return ISCEET_HW_FAULT; } |
| int x = flash_read(addr, buf, 10); | Use of 'int' not fixed-width | ISCEET_Status_t status = flash_driver_read(addr, buf, 10U); |
| #define SIZE 256 | Magic number as bare define | #define FLASH_PAGE_SIZE (256U)  /* STM32F303 flash page size in bytes */ |
