## 2. Introduction

### 2.1 Purpose

This Plan for Software Aspects of Certification (PSAC) defines the software lifecycle processes, activities, and documentation for the Intelligent Safety-Critical Engineering Environment Toolchain project. This document is the master certification planning document, submitted to the certification authority prior to commencement of any development activity.

### 2.2 Project Overview

The project consists of an AI-powered toolchain composed of six intelligent modules (M1 to M6), each automating a specific phase of the DO-178C software development lifecycle. Each module receives verified inputs and produces standardized lifecycle output documents:

| Module | Name | Input | Output Document | Output Content | DO-178C § |
|---|---|---|---|---|---|
| M1 | HLR Generator | PDS + Hardware Doc + System Architecture | SRD | Section 1: System Architecture (user-provided) Section 2: HLR...HLR | §5 |
| M2 | LLR Generator | SRD (HLRs) | SDDD | Section 1: Software Architecture (generated) Section 2: LLR...LLR | §6 |
| M3 | Code Generator | SDDD (LLRs) | /src folder | Structured source files, one per module, traceable to LLR | §7 |
| M4 | LLT Generator | SDDD (LLRs) | SUTC | Low Level Test cases derived from LLRs | §9 |
| M5 | HLT Generator | SRD (HLRs) | SVTC | High Level Test cases derived from HLRs | §9 |
| M6 | Traceability Generator | All artifacts | TM | Bidirectional traceability matrix: PDS-HLR-LLR-Code-LLT-HLT | §11 |

### 2.3 Key Architectural Decisions

The following architectural decisions govern the structure of lifecycle outputs:

- SRD contains two sections: (1) the System Architecture provided by the engineer as M1 input context, and (2) the HLRs generated by M1. This ensures full traceability from system architecture to software requirements within a single document.
- SDDD contains two sections: (1) the Software Architecture generated by M2 from HLRs, and (2) the LLRs derived from those HLRs. This co-location ensures design and requirements are always consistent.
- M3 generates source code into a structured /src folder, with one subfolder per functional module, each file explicitly traceable to one or more LLR identifiers.
- M4 reads exclusively from SDDD (LLRs) to generate structural low-level tests. M5 reads exclusively from SRD (HLRs) to generate functional high-level tests. These sources must not be mixed.

### 2.4 Scope

This PSAC covers all software lifecycle data produced by the toolchain, including requirements, design, code, tests, and traceability data. All AI-generated outputs are subject to human review and verification in accordance with DO-178C objectives.

### 2.5 Referenced Documents

- RTCA DO-178C — Software Considerations in Airborne Systems and Equipment Certification (2012)
- RTCA DO-330 — Software Tool Qualification Considerations
- RTCA DO-331 — Model-Based Development and Verification Supplement
- SAE ARP4754A — Guidelines for Development of Civil Aircraft and Systems
- SAE ARP4761 — Guidelines for Conducting Safety Assessments

## 3. Software Overview

### 3.1 System Description

The toolchain operates as an end-to-end software development and verification automation environment for safety-critical airborne software. It ingests product-level documentation and produces all required DO-178C lifecycle artifacts through a chain of specialized AI agents.

### 3.2 Software Function

- M1: Parse PDS, hardware documentation, and user-provided system architecture to generate HLRs, producing SRD
- M2: Derive software architecture and LLRs from SRD HLRs, producing SDDD
- M3: Generate structured source code from SDDD LLRs into a /src folder with one subfolder per module
- M4: Generate low-level test cases from SDDD LLRs, producing SUTC
- M5: Generate high-level test cases from SRD HLRs, producing SVTC
- M6: Aggregate all artifacts and generate bidirectional traceability matrix TM

### 3.3 Design Assurance Level (DAL)

The DAL level shall be determined by the system safety assessment conducted per ARP4761. The toolchain is designed to support up to DAL A objectives, consistent with the assumed Eengine Control like safety-critical context used for demonstration purposes. The applicable DAL for this project is:

| Software Item | Failure Condition | DAL | Rationale |
|---|---|---|---|
| I-SCEET Generated Artifacts | Incorrect or incomplete generated lifecycle artifacts | A | May introduce undetected errors affecting all downstream development phases in a safety-critical environment |
| HLR/LLR Documents | Incomplete, ambiguous, or inconsistent requirements | A | Requirement defects propagate through the lifecycle and may lead to unsafe system behavior |
| Generated Source Code | Incorrect or non-compliant implementation | A | Direct impact on system execution potentially leading to catastrophic failure in engine control context |

The assumption of DAL A is based on the FADEC-like context, where software failure may lead to catastrophic consequences affecting engine control and aircraft safety.

### 3.4 Software Partitioning

The toolchain is logically partitioned into six independent modules (M1–M6). Each module receives verified inputs and produces outputs subject to independent review. No shared state exists between modules during execution that could propagate undetected errors.

## 4. Software Lifecycle

### 4.1 Lifecycle Model

The project follows the sequential DO-178C software lifecycle model, aligned with the V-model. All planning documents must be completed and reviewed before development activities commence (SOI #1).

The lifecycle ensures full traceability from requirements to verification in accordance with DO-178C objectives.

### 4.2 Complete Lifecycle Flow

| Phase | Activities | Input | Output | SOI Gate |
|---|---|---|---|---|
| Planning | Write PSAC, SDP, SVP, SCMP, SQAP | Project requirements | 5 Planning Documents | SOI #1 |
| Standards | Write SRS, SDS, SCS | DO-178C §11.1 | 3 Standards Documents | SOI #1 |
| Requirements (M1) | Generate System Architecture + HLRs | PDS + HW Doc + System Architecture | SRD | SOI #2 |
| Design (M2) | Generate Software Architecture + LLRs | SRD | SDDD | SOI #2 |
| Coding (M3) | Generate source code | SDDD | /src folder | SOI #2 |
| Low Level Testing (M4) | Generate LLT cases from LLRs | SDDD (LLRs) | SUTC | SOI #3 |
| High Level Testing (M5) | Generate HLT cases from HLRs | SRD (HLRs) | SVTC | SOI #3 |
| Traceability (M6) | Generate traceability matrix | All artifacts | TM | SOI #3 |
| Certification | Compile SAS, final review | All lifecycle data | SAS | SOI #4 |

### 4.3 Transition Criteria

Transition from one phase to the next requires:

- All outputs of the current phase reviewed and approved by an independent reviewer
- All review action items closed or formally tracked
- Configuration management baseline established for all outputs
- Quality assurance sign-off obtained

### 6.2 Tool Qualification Strategy (DO-330)

Per RTCA DO-330, AI modules generating or verifying safety-critical outputs must be qualified. Qualification level depends on DAL and detectability of errors:

- TQL-5 applies to M1, M2, M6: tools whose outputs are verified by a subsequent human review activity
- TQL-4 applies to M3, M4, M5: tools that automate verification or code generation where errors may not be caught downstream without explicit qualification
- Each AI module shall have a Tool Qualification Plan (TQP) documenting: tool operational requirements, qualification test data, and known limitations

### 6.3 Standards Applied to AI Module Outputs

| SRS | HLRs in SRD, LLRs in SDDD | M1 and M2 prompt constraints + human review |
| SDS | Software Architecture in SDDD | M2 prompt constraints + human review |
| SCS + MISRA-C:2012 | Source code in /src folder | M3 prompt constraints + static analysis tool |

## 7. Software Verification

### 7.1 Verification Overview

All AI-generated artifacts shall be subject to independent verification before being used as inputs to subsequent modules. No module shall accept unreviewed inputs. Verification activities include reviews, analyses, and testing as defined in SVP.

### 7.2 Verification Matrix

| Artifact | Document | Source Module | Verification Activity | Reviewer |
|---|---|---|---|---|
| System Architecture | SRD §1 | User-provided | Review against hardware doc and PDS | Engineer |
| HLRs | SRD §2 | M1 | DO-178C §5 objectives: accuracy, consistency, verifiability, traceability, no ambiguity | Independent Engineer |
| Software Architecture | SDDD §1 | M2 | Review module decomposition, interfaces, data flows vs HLRs | Independent Engineer |
| LLRs | SDDD §2 | M2 | DO-178C §6 objectives: completeness vs HLR, no undocumented functions | Independent Engineer |
| Source Code | /src folder | M3 | Code review, MISRA-C compliance, structural coverage analysis | Independent Engineer |
| Low Level Tests | SUTC | M4 | Review test cases vs SDDD LLRs, structural coverage (MC/DC per DAL) | Independent Engineer |
| High Level Tests | SVTC | M5 | Review test cases vs SRD HLRs, functional coverage | Independent Engineer |
| Traceability | TM | M6 | Bidirectional check, orphan requirement detection, orphan code detection | QA + Engineer |

### 7.3 Coverage Objectives by DAL

| DAL | Statement | Decision | MC/DC | Applies to |
|---|---|---|---|---|
| A | Required | Required | Required | All /src files |
| B | Required | Required | Not Required | All /src files |
| C | Required | Not Required | Not Required | All /src files |
| D | Not Required | Not Required | Not Required | All /src files |

### 7.4 M4 / M5 Input Source Distinction

The following rule is mandatory and must be enforced throughout the project:

- M4 (LLT Generator) shall read EXCLUSIVELY from SDDD LLRs — never from SRD
- M5 (HLT Generator) shall read EXCLUSIVELY from SRD HLRs — never from SDDD
- Mixing input sources between M4 and M5 would violate DO-178C §9 verification independence objectives

## 8. Software Configuration Management

All lifecycle artifacts shall be placed under configuration management per SCMP from the moment they are created. Key rules:

- Baseline 1 (SOI #1): PSAC, SDP, SVP, SCMP, SQAP, SRS, SDS, SCS
- Baseline 2 (SOI #2): SRD, SDDD, /src folder
- Baseline 3 (SOI #3): SUTC, SVTC, TM, test results
- Baseline 4 (SOI #4): SAS, all lifecycle data complete
- Any post-baseline modification requires a formal change request and impact analysis
- Problem reports raised during verification shall be tracked to closure before the next SOI gate

## 9. Software Quality Assurance

SQA activities ensure compliance with DO-178C objectives and are defined in SQAP. Key principles:

- Process audits at each SOI gate transition
- Independence: SQA auditor shall not be the author of the artifact being audited
- SQA shall verify that no module (M1-M6) was executed before its governing standards document (SRS/SDS/SCS) was approved
- SQA shall verify that M4 only reads SDDD and M5 only reads SRD
- All non-conformances documented and resolved before SOI review

## 11. Additional Considerations

### 11.1 Derived Requirements

AI-generated HLRs (M1) may include derived requirements — requirements with no direct PDS parent. All derived requirements shall be:

- Explicitly tagged with the label [DERIVED] in SRD
- Reviewed and approved by the systems engineer before M2 is triggered
- Submitted to the safety process (ARP4761) for assessment

### 11.2 /src Folder Structure

The source code generated by M3 shall follow this mandatory structure:

- /src/[module_name]/[module_name].c — implementation file
- /src/[module_name]/[module_name].h — header file
- /src/[module_name]/README.md — traceability note listing LLR IDs implemented in this module

Each source file shall contain a header comment block referencing the LLR identifiers it implements, enabling M6 to build the traceability matrix automatically.

### 11.3 Limitations of AI-Generated Outputs

- AI models may produce plausible but incorrect requirements — mitigated by mandatory independent review before use as M2 input
- AI models may not capture all hardware constraints — mitigated by including full hardware documentation as M1 input
- Generated code may require iteration to achieve required structural coverage — mitigated by coverage analysis in M4 verification phase
- AI-generated LLRs may introduce undocumented functions — mitigated by M2 output review checking for HLR-to-LLR completeness

### 11.4 Tool Qualification for AI Modules

Since M1 through M6 are custom AI agents, they are subject to DO-330 qualification. The PSAC commits to producing a Tool Qualification Plan (TQP) for each module prior to SOI #1. TQPs will document tool operational requirements, qualification test data, identified limitations, and error detection mechanisms.
