## 2. Introduction

### 2.1 Purpose

This Software Quality Assurance Plan (SQAP) defines the quality assurance (QA) processes, organization, and activities for the Intelligent Safety-Critical Engineering Environment Toolchain (I-SCEET) project. The SQAP ensures objective verification that the software lifecycle, including the AI-generated artifacts, complies with DO-178C §8, the project planning documents, and the project standards (SRS, SDS, SCS).

This document shall be reviewed and approved prior to the creation of any lifecycle artifact and is a required deliverable for SOI #1.

### 2.2 Project Overview

The I-SCEET project produces lifecycle artifacts through six AI modules (M1–M6). The SQAP defines how SQA personnel independently verify that the planning processes, the AI modules, and the resulting artifacts comply with the applicable plans and standards at each Stage of Involvement (SOI):

| SOI | QA Focus | Artifacts Audited |
|---|---|---|
| SOI #1 | Planning conformity | PSAC, SDP, SVP, SCMP, SQAP, SRS, SDS, SCS |
| SOI #2 | Development conformity | SRD, SDDD, /src (M1, M2, M3 outputs) |
| SOI #3 | Verification conformity | SUTC, SVTC, TM, SVTR |
| SOI #4 | Final conformity | SAS and full lifecycle data audit |

### 2.3 Scope

This SQAP applies to all quality assurance activities performed throughout the I-SCEET project lifecycle, including audits of planning documents, standards documents, AI module configuration, AI-generated artifacts, human review records, and configuration management records.

## 3. Quality Assurance Organization

### 3.1 Independence Principle

Per DO-178C §8.1, Software Quality Assurance shall have the authority to ensure proper development and verification of the software, and shall have the responsibility to assess whether the established plans and standards are followed. SQA is organizationally independent from the development activities it audits.

### 3.2 Roles and Responsibilities

| Role | Responsibility | Independence |
|---|---|---|
| Quality Assurance Officer | Conducts audits, raises SQRs, approves SOI gate closure | Independent of development (M1–M3) and verification (M4–M6) authoring |
| Project Supervisor | Approves QA findings escalations and corrective actions | Independent of day-to-day generation activities |
| Author / Engineer | Implements corrective actions identified by SQA | N/A — subject of audit |
| Certification Liaison | Coordinates SQA records with the certification authority | Independent reviewer |

## 4. Quality Assurance Activities

### 4.1 Planning Conformity Audits

Prior to SOI #1 closure, SQA shall verify that all five planning documents (PSAC, SDP, SVP, SCMP, SQAP) and three standards documents (SRS, SDS, SCS) are complete, internally consistent, and approved by the required signatories.

### 4.2 AI Module Output Audits

For every artifact generated by M1–M6, SQA shall perform a conformity audit verifying:

- The artifact follows the mandatory structure defined in the governing standard (e.g., HLR format per SRS)
- The system prompt used by the module matches the approved version on record
- Traceability fields (Parent, Req, etc.) reference real, existing upstream items
- No forbidden constructs or language were used (per SRS/SCS prohibited lists)
- The model used for generation matches the assigned model for that module (independence check, see §4.4)

### 4.3 Human Review Conformity

SQA shall verify that every AI-generated artifact has received a documented human review (Approved / Needs Revision / Rejected) recorded in the project database prior to being used as input to the next module, in accordance with SVP.

### 4.4 AI Model Independence Audit

Per DO-178C §6.3, SQA shall verify that the independent verification modules (M4, M5) use a model and prompt distinct from the modules they verify (M3, M1 respectively), and that this assignment has not been altered without an approved configuration change (per SCMP §6.3).

| Generator | Independent Verifier | Audit Check |
|---|---|---|
| M1 (HLR) | M5 (HLT) | Confirm M5 model ≠ M1 model in configuration record |
| M3 (Code) | M4 (LLT) | Confirm M4 model ≠ M3 model in configuration record |

## 5. Conformity Criteria

The following checklist constitutes the minimum conformity criteria evaluated by SQA at each audit:

| # | Criterion | Reference |
|---|---|---|
| Q01 | Document follows the mandatory section structure | Governing standard / template |
| Q02 | All mandatory fields populated, no TBD/TBC | SRS §5, SDS, SCS |
| Q03 | Traceability fields reference valid upstream IDs | SRS §7 |
| Q04 | No forbidden language or constructs used | SRS §5, SCS §7 |
| Q05 | Correct model/prompt used for the module | SCMP §3.3 |
| Q06 | Human review recorded prior to next module | SVP |
| Q07 | Artifact stored under configuration management | SCMP §5 |
| Q08 | Independence preserved for M4/M5 vs M3/M1 | DO-178C §6.3 |

## 6. Non-Conformities — Software Quality Records (SQR)

### 6.1 SQR Process

Any deviation from the conformity criteria in §5 shall be recorded as a Software Quality Record (SQR). The SQR process is:

- SQA identifies and logs the non-conformity with an SQR-NNN identifier
- SQA classifies severity (Critical / Major / Minor) per §6.2
- The responsible engineer is notified and proposes a corrective action
- SQA verifies the corrective action and closes the SQR
- Open SQRs of Critical or Major severity block SOI gate closure

### 6.2 SQR Severity Classification

| Severity | Definition | Example | SOI Gate Impact |
|---|---|---|---|
| Critical | Safety, traceability, or independence violated | M4 used the same model as M3 (independence broken) | Blocks gate closure |
| Major | Standard non-compliance affecting artifact validity | HLR missing mandatory Verification field | Blocks gate closure |
| Minor | Cosmetic or documentation issue, no functional impact | Inconsistent date format in revision history | Tracked, does not block |

## 7. Audits of AI Modules (M1–M6)

### 7.1 Generation-Time Audit

Each time a module is executed (or re-executed following TC remarks), SQA shall sample-audit the generated output against the criteria in §5. The orchestrator records, for each generation: the module ID, the model used, the system prompt version, the input artifacts, the output artifact, and the timestamp — these records constitute the primary SQA evidence.

### 7.2 Re-Generation Audit

When an artifact is re-generated following Technical Comments (TC Excel) remarks, SQA shall verify that:

- Every open TC remark for the module was provided as input to the re-generation
- The new artifact version addresses each remark (model_response field populated)
- The previous version is retained in the configuration management record, not overwritten (per SCMP §6.3)

### 7.3 Drift Detection

SQA shall periodically compare the system prompt files on Google Drive against the approved baseline copies to detect unauthorized modification of an AI module's governing instructions.
