================================================================================

M3 shall generate one individual `.c` source file for each LLR.

M3 shall generate one README.md per component/subsystem.

Correct structure:

================================================================================
SOURCE FILE NAMING RULE
================================================================================

Each `.c` file shall be named exactly from the LLR ID:

LLR-<SUBSYSTEM>-NNN-XX.c

For Derived LLRs:

LLR-<SUBSYSTEM>-NNN-XX-D.c

Examples:
LLR-CLK-001-01.c
LLR-UART-002-01.c
LLR-SYS-004-01-D.c

Rules:
- The file name shall preserve the LLR ID exactly.
- Do not replace hyphens with underscores in the filename.
- Do not merge several LLRs into one `.c` file.
- Do not split one LLR across several `.c` files unless the SDDD explicitly
  requires supporting static helper functions in the same file.
- Every LLR shall have exactly one implementation `.c` file.
- Every Derived LLR shall have exactly one implementation `.c` file.

================================================================================
HEADER FILE RULE — ONE HEADER PER COMPONENT
================================================================================

Each component/subsystem shall have one public header file:

<component_name>.h

Examples:
boot_manager.h
clk_driver.h
uart_driver.h
flash_driver.h
gpio_driver.h
crc_module.h
systick_driver.h
wdg_driver.h
app_main.h
sys_handler.h

The component header shall contain:
- include guard
- required includes
- public typedefs
- public enums
- public structs
- public constants/macros
- prototypes of all public functions implemented in the component LLR `.c` files

Rules:
- Do not create one `.h` per LLR.
- Do not duplicate typedefs across several `.c` files.
- Do not declare private static helper functions in the `.h`.
- All public functions shall be declared in the component `.h`.
- Internal helper functions shall remain `static` inside the relevant LLR `.c` file.
- Shared module state shall not be exposed as unsafe extern global variables.

Example:

#ifndef UART_DRIVER_H
#define UART_DRIVER_H

#include "isceet_types.h"
#include <stdint.h>

typedef enum
{
    UART_DRIVER_BAUD_115200 = 115200u
} UART_Driver_BaudRate_t;

ISCEET_Status_t uart_driver_init(void);
ISCEET_Status_t uart_driver_configure_baudrate(uint32_t baudrate);
ISCEET_Status_t uart_driver_transmit_byte(uint8_t byte);
ISCEET_Status_t uart_driver_receive_byte(uint8_t * byte);

#endif /* UART_DRIVER_H */

    ISCEET_CRC_FAIL      = 0x05u,

================================================================================
ONE LLR = ONE IMPLEMENTATION UNIT RULE
================================================================================

Each LLR `.c` file shall implement the complete behavior of exactly one LLR.

Each LLR `.c` file shall include:
- the component header
- isceet_types.h if not already included by the component header
- required STM32 HAL/CMSIS headers only when needed
- the mandatory file header
- one public function implementing the LLR behavior
- optional static helper functions only if required by the same LLR
- trace comments for Cause/Effect aliases from the LLR
- no unrelated code

Each LLR `.c` file shall not implement:
- another LLR
- unrelated helper utilities
- hidden integration behavior
- behavior not present in the LLR Implementation section

================================================================================
MULTIPLE LLRs IN ONE FUNCTION — FORBIDDEN BY DEFAULT
================================================================================

M3 shall not merge several LLRs into one C function by default.

Preferred mapping:

LLR-CLK-001-01 -> clk_driver_configure_clock_source()
LLR-CLK-001-02 -> clk_driver_verify_clock_source()
LLR-CLK-001-03 -> clk_driver_report_clock_error()

Not preferred:

LLR-CLK-001-01, LLR-CLK-001-02, LLR-CLK-001-03 all hidden inside:

clk_driver_init()

If the SDDD explicitly requires one public orchestration function, M3 may
generate an orchestration function, but:
- the orchestration function shall not replace the one-LLR-one-file rule
- each LLR shall still have its own `.c` file
- the orchestration function shall call the LLR implementation functions
- the orchestration function shall be traced as a supporting function
- the orchestration function shall be listed in README.md

Example:

ISCEET_Status_t clk_driver_init(void)
{
    ISCEET_Status_t status = ISCEET_OK;

    status = clk_driver_configure_clock_source(E_BOOT_CLK_PLL);

    if (status == ISCEET_OK)
    {
        status = clk_driver_verify_clock_source();
    }

    return status;
}

================================================================================
CAUSES / EFFECTS IMPLEMENTATION RULE
================================================================================

The SDDD Causes / Effects table contains readable writing blocks.

Example:

| Cause Alias | Cause Writing Block | Effect Alias | Effect Writing Block |
|-------------|--------------------|--------------|----------------------|
| C1 | [The clock source is High-Speed Internal] | E1 | [Configure High-Speed Internal Clock] |
| C2 | [The clock source is High-Speed External] | E2 | [Configure High-Speed External Clock] |
| C3 | [The clock source is Phase-Locked Loop] | E3 | [Configure Phase-Locked Loop to 72 MHz] |
| C4 | [The clock source is invalid] | E4 | [Reject the clock configuration request] |

M3 shall not implement code from the writing block text alone.

M3 shall use the matching Implementation lines.

Example Implementation lines:

[C1]: {source} is equal to E_BOOT_CLK_HSI
[E1]: Set the content of {clock.freq_config.HSI} to TRUE

[C2]: {source} is equal to E_BOOT_CLK_HSE
[E2]: Set the content of {clock.freq_config.HSE} to TRUE

[C3]: {source} is equal to E_BOOT_CLK_PLL
[E3]: Set the content of {clock.freq_config.PLL} to 72000000u

[C4]: {source} is different from E_BOOT_CLK_HSI, E_BOOT_CLK_HSE, and E_BOOT_CLK_PLL
[E4]: Return ISCEET_INVALID_PARAM and keep {clock.freq_config} unchanged

M3 shall translate these pairs into C logic.

Expected code pattern:

if (<condition derived from C1>)
{
    <actions derived from E1>;
}
else if (<condition derived from C2>)
{
    <actions derived from E2>;
}
else if (<condition derived from C3>)
{
    <actions derived from E3>;
}
else
{
    <actions derived from E4>;
}

- Every Cause Alias and Effect Alias shall be implemented.

================================================================================
IMPLEMENTATION VERB TRANSLATION RULE
================================================================================

M3 shall translate SDDD Implementation actions into deterministic C code.

Supported Implementation verbs:

1. Set the content of {x} to <value>
   -> x = value;

2. Reset {x} to <value>
   -> x = value;

3. Clear {x}
   -> x = 0u; or equivalent typed clear

4. Keep {x} unchanged
   -> no write to x in that branch

5. Compare {x} with <value>
   -> if (x == value) or if (x != value), depending on cause

6. Call <function>()
   -> status = function(); return value shall be checked if applicable

7. Return <status>
   -> return status;

8. Store <value> into {x}
   -> x = value;

9. Increment {x} by <value>
   -> x += value;

10. Decrement {x} by <value>
    -> x -= value;

11. Start <timer/peripheral>
    -> call corresponding low-level or HAL/CMSIS action only if justified

12. Stop <timer/peripheral>
    -> call corresponding low-level or HAL/CMSIS action only if justified

Forbidden:
- implementing vague behavior not present in Implementation
- adding hidden behavior
- adding unrelated safety mechanisms
- ignoring No Effect branches
- ignoring invalid/default branches

================================================================================
DERIVED LLR IMPLEMENTATION RULE
================================================================================

Derived LLRs shall be implemented exactly like standard LLRs.

For every Derived LLR:
- the ID shall keep its trailing "-D" suffix
- the `.c` file name shall keep the "-D" suffix
- the file header shall include @implements with the Derived LLR ID
- the function header shall include @req with the Derived LLR ID
- README.md shall mark it as Derived = Yes
- the code shall implement the Derived LLR Implementation section
- the Derived LLR shall not be ignored because it has no [COV.HLR-xxx]

Example file:

/src/sys_handler/LLR-SYS-001-01-D.c

Example function header:

/**
 * @brief   Refresh watchdog during long CRC computation.
 * @return  ISCEET_OK if watchdog refresh is completed.
 * @req     LLR-SYS-001-01-D
 * @note    Derived LLR implementation.
 */

================================================================================
SUPPORTING FUNCTION RULE
================================================================================

M3 may generate supporting internal functions only when required to implement
one or more LLRs.

A supporting function is allowed only if:
- it is called by an LLR-implementing function
- it has a clear trace to one or more LLR IDs
- it is listed in README.md
- it is not orphaned
- it is static if it is not part of the public component API

Supporting function header format:

/**
 * @brief   <purpose>
 * @req     <LLR-ID(s) that justify this helper>
 * @note    Internal helper generated to implement LLR Cause/Effect logic.
 */

Forbidden:
- helper functions with no LLR reference
- utility functions generated only for convenience
- code paths not linked to Cause/Effect or Implementation lines
- orphan functions
- unused functions

================================================================================
MISRA-C AND SAFETY RULES
================================================================================

M3 shall comply with C99 and MISRA-C:2012 Mandatory and Required rules.

Mandatory rules:
- no goto
- no recursion
- no malloc/calloc/free
- no variable length arrays
- no printf/scanf/stdio
- no setjmp/longjmp
- no unbounded loops
- no implicit type conversions
- no magic numbers
- no unsafe extern global variables
- no dead code
- no unreachable code
- no unused functions
- no unused variables
- no multiple writes hidden in expressions
- no assignment inside condition expressions
- no fallthrough in switch without explicit comment
- all switch statements shall have default branch
- every non-void function shall return a value on all paths
- every ISCEET_Status_t return value shall be checked by caller
- every pointer parameter shall be checked against NULL before use
- every hardware access shall be justified by SDDD or DD

Allowed only if justified by SDDD:
- direct register access
- HAL/CMSIS call
- interrupt service routine
- volatile variable

================================================================================
SHARED STATE RULE
================================================================================

Static variables used only by one LLR shall stay inside that LLR `.c` file.

Shared module state used by multiple LLR `.c` files shall be declared through
a controlled module context structure.

Unsafe extern global variables are forbidden.

Preferred pattern:

typedef struct
{
    uint32_t frequency_hz;
    uint8_t initialized;
} Clk_Driver_Context_t;

Access shall be controlled by:
- static context inside one component implementation unit, or
- getter/setter APIs, or
- explicit context pointer passed to functions

If shared state cannot be implemented safely from the SDDD information,
mark the related LLR as BLOCKED.
